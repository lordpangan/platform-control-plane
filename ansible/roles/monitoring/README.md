# monitoring role

Installs **kube-prometheus-stack** on the brain: Prometheus, Grafana,
kube-state-metrics and node-exporter, with the Prometheus Operator managing
them.

| Open | Command |
|---|---|
| Grafana | `make grafana-ui-vm` → http://localhost:3000, user `admin`, password from `make grafana-password-vm` |
| Prometheus | `make prometheus-ui-vm` → http://localhost:9090 (Status → Targets, Alerts) |

## Choices

| Setting | Value | Why |
|---|---|---|
| Prometheus storage | 10Gi PVC on `standard` (kind local-path), 7d / 8GB retention | Survives pod restarts and VM reboots. Lost on a cluster rebuild (the volume lives in the kind node). |
| Alertmanager | off | No delivery target in a single-user lab. Prometheus still evaluates the rules; firing alerts show in the UIs. |
| etcd, scheduler, controller-manager, kube-proxy scrapes | off, along with their rules | kind binds them to `127.0.0.1` in the node container, so Prometheus can't reach them. Their pods' up/down and restarts are still visible through kube-state-metrics. |
| Grafana password | generated by the chart into the `monitoring-grafana` Secret | No vault entry. A rebuild generates a new one. |
| Grafana volume | none | Dashboards come from ConfigMaps (sidecar). |
| Monitor selectors | `*SelectorNilUsesHelmValues: false` | Prometheus picks up ServiceMonitors and PrometheusRules from every namespace (e.g. ArgoCD's), not only ones labelled with this release. |

## Gotchas

- **Names come from `fullnameOverride: monitoring`.** The Makefile targets rely
  on `svc/monitoring-grafana`, `svc/monitoring-prometheus` and the
  `monitoring-grafana` Secret. Change the release name and they break.
- **CRDs.** The chart installs the Prometheus Operator CRDs on first install.
  Helm does **not** upgrade CRDs, so a chart bump with CRD changes needs them
  applied by hand (see the chart's upgrade notes).
