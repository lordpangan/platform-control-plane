# 2026-08-10 — Phase 2: infra via Crossplane + Terraform (Steps 1–2)

**Goal:** teach the brain to provision real AWS infra. This entry covers the
groundwork — the state backend + identity (Step 1) and installing
`provider-terraform` (Step 2). The VPC/EKS layers come next.

## Decisions locked in (during brainstorm)

- **Community Terraform modules** (`terraform-aws-modules/{vpc,eks}`), not hand-rolled HCL.
- **S3 + DynamoDB remote state**, via a one-time bootstrap — state survives a
  cluster rebuild, so teardown is always possible (no orphaned, billing EKS).
- **Scoped IAM user** `crossplane-terraform` (service-scoped, *not* admin).
- **2× t3.small SPOT** nodes; **network as its own layer** (`XNetwork`) that
  `XEKSCluster` finds by tag; **`create_kms_key = false`** on the EKS layer
  (policy keeps `kms:*` for future use).

## Step 1 — bootstrap the state backend + identity (`bootstrap/aws-state/`)

A one-time Terraform, run with **local state** (the root of trust, gitignored) via
the `platform-engineer-admin` SSO profile. Creates the S3 state bucket (versioned,
encrypted, private), the DynamoDB lock table, and the scoped IAM user + access key.

- Auth: **IAM Identity Center (SSO)** for the human — no long-lived admin keys.
- `make bootstrap-aws` / `make teardown-aws-state`.
- Applied and verified: 9 resources, bucket versioning Enabled, lock table ACTIVE,
  policy attached.

## Step 2 — install `provider-terraform` (Ansible `providers/` role)

> **Update (2026-08-11):** the engine was switched from `provider-terraform` to
> `provider-opentofu` the next day — Terraform is frozen at 1.5.x under the BSL,
> OpenTofu (1.10) is the open replacement. See the 2026-08-11 entry. The role is
> engine-agnostic now; the mechanics below still hold, just s/terraform/opentofu/
> on the provider + API group.

The example `install.yaml` upstream was stale, so I didn't copy it:

- It pinned **v0.2.0** and a **`ControllerConfig`** (deprecated ~Crossplane 1.14,
  replaced by `DeploymentRuntimeConfig`). We install **v1.1.1** with *no* runtime
  config — we don't need to tune the pod yet.
- Crossplane v2 is namespaced, so the provider serves a namespaced API
  (`tf.m.upbound.io`). Our Workspaces will be namespaced, so they reference a
  cluster-scoped **`ClusterProviderConfig`** — one config + one Secret shared by
  every namespace (confirmed cluster-scoped: `api-resources` shows
  `NAMESPACED=false`).

The role: install the `Provider`, wait Installed+Healthy, wait for the CRD, then
wire the AWS creds `Secret` (pulled from local TF state on the controller) and the
`ClusterProviderConfig`. The creds step **skips cleanly** if the bootstrap hasn't
been run, so `make up` still stands up the brain without AWS.

Verified on the VM: provider `Installed=True Healthy=True`, Secret + CPC present,
`workspaces.tf.m.upbound.io` available.

## Bugs hit and fixed (the "learn by doing" part)

1. **PATH on a delegated task.** The play forces the *target's* PATH everywhere.
   The one task that runs on the controller (`terraform output`, `delegate_to:
   localhost`) then couldn't find `terraform` (it's on the Mac, not the VM). First
   run installed the provider but *skipped* creds. Fix: reset `PATH` to the
   controller's real PATH (`lookup('env','PATH')`) on that task.
2. **Secret task falsely non-idempotent.** `kubectl apply` of a Secret always
   reports `"configured"`, never `"unchanged"`, so `changed_when` fired every run.
   Rewrote it to compare desired-vs-current (base64) and only write on a real diff.
   Debugging also revealed the old `$(printf …)` was **stripping the trailing
   newline** (111 vs 112 bytes) — and my first hash-based diagnostic was fooled by
   the *same* bash `$(...)` newline-stripping. `cmp` on files settled it.

## Day-2 tests (all green)

- **Re-apply:** `changed=0` (idempotent).
- **Modify:** region change updated *only* the ClusterProviderConfig in place
  (provider + Secret untouched), then reverted.
- **Delete + recreate:** deleted CPC + Secret → re-run rebuilt both; provider
  stayed Healthy.
